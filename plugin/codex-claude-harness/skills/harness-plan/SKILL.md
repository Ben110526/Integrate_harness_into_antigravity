# Plan workflow

1. Read repository instructions, git status, and the relevant code paths.
2. Recover cumulative task intent across turns, requested outcomes, constraints, non-goals and observable checks. Follow-ups refine the active task; status questions and compaction do not reset earlier requirements. Preserve prior authorization; disclose inaccessible context. Resolve evidence in this order: the user's explicit request; repository instructions and public contracts; tests and types; call sites and current behavior; version-matched authoritative documentation; labeled assumptions.
3. Map every explicit user requirement and constraint to stable IDs (`AC-1`, `AC-2`, ...) with observable acceptance and a relevant check. Do not omit, merge away, dilute, or invent requirements. Before product edits outside the inline fast path, main registers `harness-task-contract.json` in the observed artifact directory using available `write_to_file` (`IsArtifact: true`, JSON `CodeContent`) or native `write_file` (absolute `Path`, JSON `Content`): `{"version":2,"taskId":"task-1","revision":1,"requirements":[{"id":"AC-1","request":"exact user excerpt","acceptance":"observable expected behavior","verification":"behavioral","sourceStep":3}]}`. Use observed originating user steps and `static` for static acceptance only. Preserve unchanged rows across turns; increment revision sequentially. Append missing criteria in the same turn only before the first task product write. Revised/dropped old IDs require explicit later user scope and `scopeChanges:[{"id":"AC-1","request":"exact latest user quote"}]`; never reuse retired IDs. An explicitly replaced task starts revision 1 with `replacesTask:{"taskId":"prior-id","request":"exact latest user replacement quote"}`. Carry the full active contract through all handoffs; never store credentials/private configuration. See `docs/task-completion.md` in the harness source for schema and limits.
4. Invoke an independent reviewer before product writes to compare the full cumulative request with the acceptance inventory, including constraints/error paths. Main persists its `phase: scope` report with matching taskId/revision, all coveredIds and unmappedRequests as `harness-acceptance-review.json`; resolve omissions and renew review after revisions. An empty unmapped list requires actual independent assessment. Delegate other independent read-only discovery when useful.
5. Identify current behavior, root problem, affected interfaces/data, migration risk, and test surface.
6. Produce a short ordered plan with concrete files/components and verification for each stage. When multiple branches can progress independently, coordinate them as described below.
7. Verify cited source paths and symbols before treating them as facts. Label only non-established claims as `[HYPOTHESIS]`, `[ASSUMPTION]`, or `[UNRESOLVED]`; do not present missing evidence as established. Do not invent requirements or business rules. Expose conflicts between sources. A labeled assumption cannot establish acceptance; a missing material rule requires main-owned clarification before dependent implementation.

If an undiscoverable decision would materially change product behavior, architecture, security, data, cost, or an irreversible action after the evidence and cheapest safe check are exhausted, use `harness-clarify` for one bounded user choice. Do not use clarification as a substitute for repository discovery.

If the user requested both planning and implementation, continue into implementation after the plan unless a missing decision would materially change the result. If the request is plan-only, remain read-only.

## Parallel assignments

Keep one row per branch in the coordinator's existing plan. Record the owner, assigned ACs or research question, writable paths (or read-only scope), dependencies, completion check, and current status. For two or more independently implementable and testable deliverables with disjoint writable paths, assign a separate implementation worker to each. This also applies to small deliverables on the normal `IMPLEMENT` route. Resolve a shared writable interface or fixture first when downstream work depends on it.

- **Ordinary conversation.** After scope passes, dispatch all ready implementation owners with separate `invoke_subagent` calls before waiting for one to finish. If capacity limits concurrent workers, dispatch the remaining owners as slots open. A failed dispatch is a blocker until another worker actually takes ownership. Give each worker the full active ACs plus its own brief. Relay decisions affecting another branch through the coordinator using known conversations. Update the plan when a worker reports changed paths, check results or a blocker. No shared file or monitor process is needed.
- **Active native Swarm.** When the user starts `/swarm` and the client exposes the board, put the same briefs and updates there. Reuse members by role, with separate read-only reviewer and verifier for complex delivery. Add a missing role within that team. A mention of Swarm in a normal prompt does not activate a board. If the user explicitly requires native Swarm and it is unavailable, report that limitation.
- **Interrupted worker.** On a 429 or timeout, keep the assignment, its working copy and its partial diff. In the plan retain the owner from the original dispatch, actual writes and checks, handoffs already received, the next unfinished action and any provider retry time. Continue other ready branches. An interrupted send may still have reached the coordinator. Check the existing conversation for the owner's actual report before sending again. A successful file write or test leaves the handoff pending until that report arrives.
- **Resuming.** Honor a provider retry or reset time. When service is available, continue the same coordinator conversation in its original workspace and contact the known owner with `send_message` or its active board. Request just the missing handoff if the edit is complete. Keep a single active writer per path. Transfer ownership only after the previous owner has stopped editing and acknowledged the transfer, or the client confirms the assignment has ended. Preserve any isolated working copy before transfer and identify the original author.
