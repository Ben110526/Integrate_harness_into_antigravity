name: harness-implement
description: Implement a requested code or configuration change with scoped edits, proactive delegation, and risk-proportionate verification.

# Implementation workflow

1. Load repository instructions and inspect current git state.
2. Define observable acceptance criteria from cumulative task intent before editing. Map every earlier and current user requirement/constraint without omission or dilution to stable IDs (`AC-1`, `AC-2`, ...); status questions or compaction do not reset the task. Before product edits outside the inline fast path, main registers version-2 `harness-task-contract.json` using the `harness-plan` format and persists independent full-request scope review as `harness-acceptance-review.json`. Preserve taskId, sequential revision, all active IDs, sourceStep, exact request excerpts, acceptance and verification across turns/handoffs. Amend omitted criteria before the first task write; revised/dropped old criteria or task replacement require explicit later user scope and the protocol's scopeChanges/replacesTask entries. Never reuse retired IDs or invent inaccessible context. Resolve evidence by explicit request, contracts, tests/types, call sites/behavior, authoritative docs, then labeled assumptions; expose conflicts. Missing material rules require main-owned clarification before dependent work.
3. Classify the change by risk, not file count. Use the policy's inline fast path only when every tiny-edit condition is established; size never overrides risk. Treat public interfaces, auth/permissions, persistence/schema/migrations, configuration or operator workflows, concurrency, security-sensitive behavior, dependency/platform migrations, coupled components, high blast radius, or uncertain acceptance criteria as normal or complex work.
   A fully specified new or unfinished isolated local API may use normal `IMPLEMENT` after inspecting call sites/integrations and establishing no integration consumers or material compatibility, external-state, auth/security, dependency/platform, concurrency or migration risk. Public tests alone are not production integration consumers. Breaking or consumer-facing interface changes and uncertain impact remain `COMPLEX_IMPLEMENT`. This changes orchestration, not inline eligibility or v2 acceptance: retain the full cumulative AC inventory, independent pre-write scope review, independent per-AC delivery assessment and fresh behavioral checks. Do not lower risk merely because the diff is short.
4. For a bug or regression, before editing product code capture a focused test or safe reproduction that fails for the expected reason (red). If that is unsafe or infeasible, state the reason and use the strongest feasible falsification check; do not manufacture failure for documentation-only, mechanical, or configuration work. After the fix, rerun the same check unchanged and require it to pass (green), then run relevant surrounding checks. For new or changed behavior, add or update the narrowest useful test before product code when the repository supports it.
5. For complex work, invoke a researcher and form a short evidence-based plan before implementation. Assign non-overlapping ownership to independent tasks. For normal low-risk `IMPLEMENT`, main implements directly after the independent verifier passes scope. Delegate to `harness-implementer` when the user explicitly requests delegation or independent parallel ownership or context isolation materially helps; do not add an implementation handoff merely to satisfy a role label. Scope/delivery assessment remains independent: main cannot assess its own delivery. If implementation reveals complex risks, promote before dependent edits and apply the complex workflow. This author choice does not change inline eligibility, cumulative v2 acceptance, scope-before-write, current checks, fresh delivery review or Ask permissions.
6. Apply the smallest coherent change that solves the requested behavior and root cause. Update operator documentation when workflow or configuration behavior changes. Invoke `harness-documenter` for required public consumer API documentation, operator workflow documentation or release-note deliverables. An isolated local API with no integration consumers and no documentation deliverable does not require a ceremonial documenter invocation. This does not waive requested documentation or documentation needed by actual consumers/operators. Mock data, stubs, placeholders, bypassed assertions and weakened tests cannot count as delivered behavior.
7. After the final workspace write, run the narrowest safe static or behavioral check that covers the changed scope, then broader checks only when their signal justifies the cost. An inline prose/comment/static-doc edit needs one static check; executable source still needs an existing focused behavioral check. Missing, failed, or inconclusive focused evidence promotes an inline edit instead of weakening verification. If no relevant safe runnable check exists, confirm that from the repository's instructions and tooling before recording `HARNESS_NO_RUNNABLE_CHECK: <specific reason>`; disclose this waiver as skipped evidence, never as a pass.
8. After a complex implementation, invoke an independent reviewer and verifier in parallel; every registered implementation needs independent per-AC delivery assessment. For normal registered `IMPLEMENT`, start the read-only independent `harness-verifier` for scope review before product writes; implementation waits for a passing scope report. After main or delegated implementation and main's final focused check bundle, resume that known existing verifier conversation via `send_message` for a fresh delivery assessment. Supply the current revision, full active AC inventory, final diff and observed final check bundle again; never reuse a scope summary as delivery proof or search for another agent conversation. The verifier stays independent from implementation. Complex review/verifier parallelism and inline exclusions are unchanged. Supply cumulative user intent, final contract, exact diff, relevant source contracts and runnable checks. Main persists the `phase: delivery` report as `harness-acceptance-review.json` with matching taskId/revision, all active id/status/evidenceSteps rows, a nonempty relevance/gap reason for each, and unmappedRequests. Resolve findings with a bounded follow-up, rerun affected checks on the resulting state, and renew delivery review after the final product write. A broad suite counts only for ACs it actually exercises; do not paste the same passing step onto unrelated criteria.
9. Review the final diff for unrelated changes, exposed secrets, incomplete branches, and compatibility regressions.
10. Before the final handoff, reconcile the current contract, scope/delivery reports and observed check IDs. If Stop requests a correction, repair only invalid fields and retain valid scope/reviews/evidence; do not rerun checks solely to repair a result envelope or restart orchestration. A correction replaces the previous response; do not quote or concatenate an earlier envelope. Only main emits the final `HARNESS_RESULT`; workers return evidence without that marker. Report the outcome, exact commands and results, residual untested risk, and an `AC-ID -> evidence/check -> result` matrix when an acceptance ledger exists. Verify source-path and symbol claims before citing them; label non-established claims `[HYPOTHESIS]`, `[ASSUMPTION]`, or `[UNRESOLVED]`, and never turn missing evidence into a fact. For a registered contract, end with one single-line `HARNESS_RESULT:` JSON object containing matching `taskId` and `revision`, top-level `status` (`complete|partial|blocked`) and `requirements` with every registered ID exactly once. Each row has `id`, `status` (`passed|failed|blocked|unverified`), `evidenceSteps` (observed tool `stepIdx` integers), and a `reason` for every nonpassed status. A passed row needs relevant successful evidence after registration and the final workspace write; behavioral criteria need behavioral evidence. Rerun checks in main when worker evidence is not observed there. Disclose later failures, exact commands and observed results; never invent evidence or exit statuses. Only all-passed permits `complete`; report exact counts, so 2/4 means partial. Never commit or push unless explicitly requested.

If an undiscoverable decision would materially change product behavior, architecture, security, data, cost, or an irreversible action after the evidence and cheapest safe check are exhausted, finish or delegate independent work before using `harness-clarify` for one bounded user choice. The dependent path pauses after invocation while already-running subagents may continue; do not fabricate ambiguity or infer consent.
